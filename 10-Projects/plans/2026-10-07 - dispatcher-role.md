# Planning Brief: роль «Диспетчер» у веб-порталі

## 1. Mission

- Problem: потрібні створення й супровід власних замовлень та розширена звітність без адміністративних прав.
- Why now: підтримати роботу диспетчера через веб-портал VanGo.
- Outcome: додаткове право «Диспетчер» у `webUserPortal`, із серверним обмеженням даних.

## 2. Success Criteria

- [ ] Диспетчер створює замовлення та бачить виконання через чинний механізм.
- [ ] Звіти, деталі, підсумки й довідники містять лише дозволені дані.
- [ ] Підміна ID або параметрів не розширює доступ; адмінські операції недоступні.
- [ ] Адмін надає й відкликає право; наступний запит використовує актуальний стан БД.
- [ ] Зберігаються можливості Замовника та поведінка чинних ролей.
- [ ] Мобільний застосунок, його API-контракти й перегляд фото залишаються без змін.
- [x] Погоджено виняток для чинних публічних URL фото у v1 (секція 5).

Non-goals:

- Мобільна роль диспетчера, зміни мобільного коду, компанії, автопарк, пряме призначення водія, експорт.

## 4. Scope

In scope:

- Право `isDispatcher`, адміністративне керування ним, серверна авторизація веб-звіту.
- Особисті замовлення, чинне створення й супровід, реальні звіти в `webUserPortal`.
- Наявні поля звіту, фільтри періоду й водія, серверні підсумки та пагінація.
- Усунення обходів доступу через параметри списків і ID; посилання на фото у звіті повертаються лише для дозволених замовлень.

Out of scope:

- Будь-які зміни мобільного коду, нова мобільна роль або звіт, зміна чинної мобільної поведінки.
- Спільна компанія, керування водіями й автомобілями, пряме призначення, експорт.

Blast radius:

- Backend моделей, авторизації та звітності; новий веб-портал; чинний адмінський UI керування користувачами.
- Зміни backend мають зберігати мобільні контракти; загальне закриття `/uploads` не авторизоване цим scope.

## 5. Assumptions

Confirmed decisions:

- Назва — «Диспетчер»; роль представлена лише у веб-порталі.
- «Свої» — створені конкретним диспетчером. Кілька диспетчерів працюють незалежно.
- Отримання замовлень водіями залишається чинним.
- Наявні поля звіту, звіт за водіями й підсумки включені; експорт виключений.
- Уточнення користувача: вигляд адмінського звіту зі скриншотів — виконані замовлення, відстань, середній час, графік за днями, оцінки та таблиці водіїв і замовлень. Усі показники обчислюються сервером лише за власними замовленнями, незалежно від сторінки.
- Адмін керує додатковим правом; можливості Замовника зберігаються.
- Цільовий клієнт — `webUserPortal`; мобільний застосунок залишається як зараз, лише Замовник і Водій.
- Користувач явно погодив виняток для фото у v1: чинні публічні URL та `/uploads` залишаються доступними для збереження мобільної поведінки. Прямий доступ за відомим URL не захищений авторизацією; це прийняте обмеження, а не виконання вимоги повного серверного захисту фото.

Verified assumptions:

- Робоча роль та адміністративне право вже розділені через `role` і `isAdmin`.
- Команди впливають на видимість, але відповідність сутності компанії не доведена.
- Новий портал інтегрує замовлення, проте звіти містять демонстраційні дані.
- Фото замовлень доступні через публічний `/uploads`.

Технічні припущення для погодження через review:

- `isDispatcher` зберігається незалежно від перемикання робочої ролі; звіт завжди використовує особистий scope.
- Наявні права водія є окремим джерелом доступу, яке `isDispatcher` не розширює.

Open questions:

- Немає.

Blockers:

- Немає. Виняток для фото погоджений користувачем у чаті.

## 7. Approach

| Option | Pros | Cons |
| --- | --- | --- |
| Окрема роль DISPATCHER | Явний тип ролі | Зміни ENUM і численних CUSTOMER/BOTH перевірок; ризики сумісності мобільного клієнта. |
| Додаткове право isDispatcher | Відповідає чинній моделі прав; зберігає робочу роль | Потребує окремого middleware та серверного scope. |

Recommendation:

- `isDispatcher: BOOLEAN NOT NULL DEFAULT false`; ENUM `UserRole` не змінювати. UI-назва — «Диспетчер» лише у вебі.

### Матриця прав

| Можливість | Замовник | Диспетчер | Адмін |
| --- | --- | --- | --- |
| Створення/супровід власного замовлення | Так | Так | За чинною робочою роллю |
| Розширений звіт | Ні | Особисті замовлення | Глобальний |
| Чужі замовлення через право диспетчера | Ні | Ні | Чинний адмінський доступ |
| Керування користувачами, командами, комісіями | Ні | Ні | Так |
| Надання/відкликання isDispatcher | Ні | Ні | Так |
| Виконання як водій | За робочою роллю | За робочою роллю | За чинними правилами |

### Модель і керування правом

- Оборотна міграція поля; всім чинним користувачам `false`. Новий ENUM і модель компанії не потрібні.
- `PATCH /admin/users/:id/dispatcher-access`, тіло `{ enabled: boolean }`, за чинною адмінською перевіркою. Надання для CUSTOMER/BOTH; іншому користувачу спочатку надати робочий режим Замовника.
- Право повертати в `/auth/me` й адмінському списку. Самостійні register/profile/role endpoints не можуть його змінювати.
- Перевіряти право з БД на кожний звітний запит. Відкликання зберігає замовлення та звичайні права.

### Межі даних

- Обов'язковий серверний predicate `customerId = req.user.id` для звіту диспетчера, його деталей, агрегатів і довідників. Клієнтські customerId/groupId/scope не є джерелом повноважень.
- Не змінювати групову видимість чинних мобільних customer endpoints. Для веб-диспетчера додати окремі scoped read endpoints `/dispatcher/orders` і `/dispatcher/orders/:id`; перевіряти право та власника сервером.
- Створення й customer-операції використовують чинні endpoints із перевірками власника. Права водія й життєвий цикл не розширюються.
- `listMyOrders`: відхиляти невідомий role з 400 і перевіряти допустимий робочий режим; валідні мобільні сценарії залишити сумісними.
- DTO через whitelist; службові поля користувачів, паролі й токени не повертати.

### API звіту

- Винести розрахунки `buildOrderAnalyticsReport` у сервіс із обов'язковим scope: глобальний для адміна, особистий для диспетчера. Чинний адмінський контракт зберегти.
- `GET /dispatcher/analytics/order-report`: authenticate + актуальне право. Фільтри `days`, `dateFrom`, `dateTo`, `driverId`; пагінація `page`, `pageSize` (1/50, максимум 100).
- Валідувати дати й порядок діапазону, додатні цілі ID/пагінацію; default 30 днів. Новий API використовує UTC календарні межі, явно позначені в UI.
- Наявні секції плюс `pagination` і серверні `totals`. Пагінувати orderRows; підсумки/driverRows рахувати за повним дозволеним набором із фільтрами.
- Довідник водіїв — лише з дозволених замовлень за періодом до фільтра driverId. Чужий driverId дає порожній результат без даних про водія.
- Статуси, маршрут/вантаж, дати етапів, тривалості, відстань, суми, фото й оцінки — за фактичним backend. Відсутній етап означає невідоме значення; кандидат/резерв не позначається призначеним водієм.
- Виправити fallback суми для відсутнього finalPrice; справжній нуль зберегти. Не додавати непідтверджені backend показники простою/затримки з demo UI.

### Веб-інтерфейс

- Використати чинний кабінет Замовника `webUserPortal`, актуальний профіль і scoped endpoints для списків/деталей диспетчера.
- Замінити demo звіти реальним API, додати пагінацію, серверні підсумки, порожні/помилкові стани й реакцію на 403 після відкликання.
- Звичайному Замовнику не показувати demo розширеної звітності. Право водія або адміна не виникає через меню Диспетчера.
- Перенести структуру таблиць і форматування чинного звіту в React; не викликати `/admin/orders` або інші глобальні API для диспетчера.
- Додати керування правом у чинному адмінському UI.
- Фото: повертати посилання лише у серверно обмежених рядках/деталях дозволених замовлень. Чинний публічний `/uploads` зберегти; захищений download endpoint і зміни мобільного клієнта у v1 не входять.

## 10. Verification Plan

- Scope-targeted checks: веб-диспетчер створює замовлення; водій отримує його чинним способом; власник бачить виконання й завершує за чинними правилами.
- New or changed tests: backend integration tests із тестовою БД для права, scope, фільтрів/пагінації; UI-перевірки реальних звітів та відкликання.
- Другий диспетчер, сторонній Замовник і член тієї самої команди не потрапляють у особистий звіт/scoped деталі.
- Підміна ID, role, scope, customerId, groupId, driverId, дат і пагінації не розширює доступ.
- Перевірити списки, деталі, підсумки й довідники; без токена 401, без права 403. Звіт/деталі не видають посилань на чужі фото. Прямі публічні URL залишаються доступними за погодженим винятком, їх не трактувати як захищені.
- Відкликання з чинним токеном блокує наступний звіт; звичайні customer можливості працюють.
- Перевірити CUSTOMER, DRIVER, BOTH, legacy ADMIN і PortalAdmin; dispatcher не має глобальних адмінських операцій.
- Перевірити порожні дані, відсутні етапи, finalPrice null/0, стабільне сортування createdAt DESC/id DESC і підсумки між сторінками.
- Перевірити up/down міграції та збереження даних.
- Регресійно перевірити чинні мобільні API-сценарії й фото без змін мобільних файлів. Не додавати мобільної ролі/звіту.
- Touched modules: backend auth/orders/admin/report; webUserPortal customer/reports; web-portal admin users.
